## 1. Project Overview

**What we are building:** An agentic outbound pipeline that finds small-to-medium CROs worldwide — and, since 2026-10-09, independent clinical research sites and SMOs (Section 9, Workflow 1b; Section 12) — enriches and scores them against our ICP, drafts personalised outreach, and sends and tracks it. Since 2026-10-03 an email draft that passes every check approves itself; a human reviews the exceptions queue — what the checks held, and every LinkedIn DM — and reads a daily digest of what went out (Section 9, Workflow 5).

**Why:** Nova Agent Kit is built and live at two CROs. The remaining problem is purely distribution. Manual prospecting does not scale; this replaces ~8 hours/day of manual work with a short morning pass over the exceptions queue and the digest.

**Secondary goals (equal weight):**
- Learn n8n, self-hosted agent orchestration, and local LLM inference
- Produce a portfolio-grade project
- Run at near-zero cost

**Endgame:** Nova Scout retargeted (CRO → pharma sponsor) becomes a second sellable product to existing Nova clients. Not before it has produced our own first 10 clients.

## 3. Hardware & Model Config — LOCKED

**Machine:** RTX 4060 Ti 16 GB VRAM · Ryzen 5 3600 · DDR4-3000

**Binding constraint:** memory bandwidth (~288 GB/s), not compute. Model must fit entirely in 16 GB VRAM — CPU offload onto DDR4-3000 is unacceptably slow.

**Model rule — ONE MODEL FOR THE ENTIRE PIPELINE.**
Running different models per node causes Ollama to evict and reload weights on every switch. Load time exceeds generation time. One model, always resident.

**LOCKED CHOICE: `qwen3.5:9b` at Q4_K_M (6.6 GB).** Leaves ~9 GB headroom for KV cache.

**What does NOT fit on 16 GB — do not attempt:**

| Model | Q4 footprint | Verdict |
|---|---|---|
| Qwen3.5/3.6/3.8 **27B** | ~15–17 GB | Exceeds VRAM before KV cache. Partial CPU offload on DDR4-3000 → unusable batch speed. |
| Qwen3.5/3.6 **35B-A3B** (MoE) | ~19 GB | All 35B must load even though only 3B activate. Does not fit. |
| Any 27B at Q3 | ~13 GB | Fits, but quantization damage makes it worse than a comfortable 9B. |

**Prompt caching — ON since 2026-10-08, one breakpoint per call, settings read from the live docs that day rather than carried forward.** Every value below was looked up or measured on 2026-10-08, because the old entry here ("no prompt caching") rested on a 2026-10-02 reading that is partly out of date and on a 5-minute lifetime that is only half the story.

| What | Value | How it was established |
|---|---|---|
| Minimum cacheable prefix | **512 tokens** for `claude-sonnet-5-5` | Live prompt-caching docs. **Not monotonic across generations** — 512 here, 1,024 on Sonnet 5, 2,048 on Opus 4.7, 4,096 on Opus 4.6 and Haiku 4.5 — so it must be re-read per model, never assumed to fall over time. A prefix under the minimum caches nothing **and raises no error**. |
| Lifetime | **5 minutes** default; `"ttl": "1h"` for an hour | Live docs. Measured from the **start** of the request that writes or reads, so generation time counts against it. A read refreshes the timer free. |
| Request format | `cache_control: {"type": "ephemeral"}` on a content block; at most 4 breakpoints; render order `tools` → `system` → `messages` | Live docs |
| Write price | 1.25× base for 5 min ($2.50/MTok), 2× for 1 h ($4/MTok) | Live pricing page |
| Read price | **0.05× base = $0.10/MTok** | Live pricing page. This doc said $0.20 until today; that is Sonnet 5's rate. |
| Verification fields | `usage.cache_creation_input_tokens`, `usage.cache_read_input_tokens`, and `usage.cache_creation.{ephemeral_5m,ephemeral_1h}_input_tokens` | Live docs; read out of n8n's own execution records by `n8n/drafting/cache_report.py` |

**Where the breakpoint goes, and what actually caches.** One breakpoint, on the last (only) system block, at every call site. The system prompt is the only text that is byte-identical across leads and runs — the generators substitute it at build time — and everything per-lead is in the user message, after it. **The cached prefix is bigger than the prompt:** measured, drafting caches **2,224** tokens where its system prompt is 1,818, because `output_config.format`'s schema renders into the prefix and caches with it. Cached share of input: drafting **58 %**, claim check **54 %**.

| Call site | System prompt | Cached? |
|---|---:|---|
| Drafting (`code_assess.js`) | 1,825 tok | yes — 2,224 with the schema |
| Claim check (`code_approval.js`) | 1,080 tok | yes — 1,522 with the schema |
| Follow-up composer (`code_followup.js`) | 1,169 tok | yes |
| **Repair** (`code_approval.js`) | **448 tok** | **no — under the 512 minimum.** It would cache nothing, raise no error, and still bill the write premium on every repair. Padding a prompt to win a few cents is the wrong trade. |

**The 5-minute TTL is a measured choice, not the default taken on trust.** The saving comes from reads, and a read needs two calls sharing the prefix inside the window. The real call pattern, read out of n8n's execution history: calls arrive in **bursts of two runs 0.1–2 minutes apart**, and the bursts themselves are **57–60 minutes** apart or several hours apart. A 5-minute entry catches every read that actually happens, at a 1.25× write; a 1-hour entry costs 2× to write and would only earn more if those 59.9-minute gaps landed inside a 60-minute window measured from the writing request's *start* — a coin flip not worth 60 % more per write. Both generators pin the value, so changing it means changing the build and this section together.

**Pre-warming is impossible here, and that was measured, not assumed.** The documented `max_tokens: 0` warm-up would be simpler than anything else: one call writes the entry and then every call in the batch reads it. It cannot be used, because `max_tokens: 0` is rejected together with structured outputs — `400 output_config.format cannot be set when max_tokens is 0` — and `format` is part of the cached prefix. A warm call without it wrote 1,818 tokens and the real call with it read **0** of them and wrote its own 2,224. Every call site here needs the schema, so no warm call can ever produce an entry they would read.

**Caching cannot change what a draft says**, and that is structural rather than hopeful: `cache_control` is a billing instruction *about* a prefix, not part of it, and the bytes the model reads are identical either way. The generators assert it: exactly one breakpoint, on the system block, never on anything in `messages`, and the 448-token repair prompt left bare. Seven mutations of those rules are each proven to refuse the build.

**Note on the price:** Sonnet 5.5 costs 2× Haiku 4.5 ($1/$5), not less. It is chosen anyway because drafting volume is 10–20/day. At that volume, capability wins and price is noise. Measured cost is in Section 4.

**Rule for model selection across this project:** pick by capability where volume is low, pick by price only where volume is high. Never route the high-volume enrichment or scoring nodes to a paid API — that is what the local 9B exists for.

Never step up to a larger local parameter count on this card. Higher-quality quant of a smaller model beats a starved larger one.

**Required Ollama environment variables (set as Windows system env vars):**

**Structured output:** always use Ollama's `format: json` with an explicit schema for extraction and scoring nodes. Never parse free text.

**Inference tuning — three gotchas that will bite otherwise:**

1. **Override the default `presence_penalty`.** Qwen3.5 ships with `presence_penalty: 1.5`. **Tested correction:** the failure mode is NOT malformed JSON as originally guessed here — Ollama's grammar-constrained `format: json` mode makes syntactically invalid output impossible, which masks the problem. The real failure is silent, field-level data loss on copy-from-source fields: at 1.5, `founder_linkedin` and `therapeutic_areas` entries came back null/truncated even when clearly present in the source text, because the penalty discourages "repeating" tokens the model is meant to be copying, not generating. Output is valid-looking JSON with quietly missing data — more dangerous than a visible parse error, since it can pass silently into scoring. At `presence_penalty: 0`, all fields extracted correctly. For extraction and scoring nodes set `presence_penalty: 0`, `temperature: 0.1`. For local drafting (v1–v2, retired 2026-10-02 — drafting is on the API now, see the ladder above), `temperature: 0.45`, `presence_penalty: 0.3` — corrected from an original guess of 0.7 after Sprint 4 testing: at 0.7 the model fabricated ("our own staff data"), joined unrelated facts into an untrue claim, and on one lead inverted the entire pitch — telling the prospect they already owned the product being sold. 0.45 fixed it; verified against real failure examples, not reverted on guesswork.

2. **Cap the context window at 16K–32K.** These models advertise 262K native context. Do not use it — KV cache at full context adds 4–8 GB and will push you off the GPU. Scraped pages are 5–20K tokens; 32K is generous.

3. **Thinking mode — tested WRONG in the original version of this doc.** For this build, thinking is ON by default, not off. Two compounding traps: omitting `think` entirely burns the whole token budget on reasoning traces and returns empty content. Worse — on `/api/chat`, setting `think:false` silently disables `format` schema enforcement, so the model answers in free prose instead of structured JSON, with no error. Keeping thinking on to preserve JSON enforcement works but costs 30–50s/lead. **Use `/api/generate`, not `/api/chat`, for structured extraction** — it honours `think:false` together with the schema correctly, same valid output in ~5s. This is load-bearing for every future Ollama structured-output node (scoring rationale, drafting) — verify it still holds on that model/endpoint before assuming it, don't just copy the setting forward blind.

**Parallelization principle, confirmed by real testing:** only the GPU call needs to be serial (`OLLAMA_NUM_PARALLEL=1` still holds for inference). Fetching/I/O steps do not — running them serially when they don't need to be caused a real failure (10 dead-domain fetches serially blew a 300s task-runner timeout; fetching 5-at-a-time dropped that batch from 305s to 46s). Apply this shape to Workflow 3 and 4 too: parallelize lookups/fetches, serialize only the model call.

**n8n activation — there is no "Active" toggle, use Publish.** n8n 2.0+ replaced the classic active/inactive flag with a draft/published model, confirmed in official docs — this applies to Community Edition, not just enterprise plans. The UI element is a **Publish** button (near the workflow name, alongside Save), not a switch. Running `publish:workflow` from the CLI leaves a misleading half-state: `workflow_entity.active` flips true and the UI can show it as published, but the actual trigger-registration tables stay empty — no cron is registered with the running process, and it silently never fires. **Always publish via the n8n UI**, never the CLI, for anything that needs to run on a schedule. `active` in the DB does NOT gate a one-off `n8n execute --id=...` run — that works regardless of published state.

**Publishing locks to a specific version.** If the workflow is regenerated and re-imported after being published (which happens routinely here — build_workflow.py has rebuilt this workflow multiple times for fixes), the publish goes stale and must be redone against the new version. Re-publish after every workflow rebuild, not just once.

**Verification — the publication tables are a dead end on this instance, don't check them.** `workflow_publication_trigger_status`, `workflow_published_version`, and `workflow_publication_outbox` only get written when `useWorkflowPublicationService` is true. It defaults to false and `N8N_USE_WORKFLOW_PUBLICATION_SERVICE` isn't set here, so those tables stay empty regardless of whether activation actually worked — checking them proves nothing on this instance. **The real signals**, confirmed by reading the running source directly: `workflow_entity.active='t'`, `activeVersionId` non-null, `triggerCount` equal to the workflow's number of triggers (below), a new row in `workflow_publish_history`, and — the only fully conclusive proof — an execution with `mode='trigger'` (the execution column is `mode`, not `trigger_mode`; the value for a fired schedule is `'trigger'`, not `'cron'`). `triggerCount=0` on its own is not evidence of a broken trigger node — it's set only after successful activation, so it reads zero on any never-activated workflow no matter how correctly built.

**`triggerCount` is a count, not a flag — check it against the workflow's trigger nodes, not against 1.** Read from `countTriggers()` in n8n 2.35.7's `active-workflow-manager`: every trigger node except Manual, plus every polling node, plus every distinct webhook node. A single-schedule workflow reads 1. **Mailbox Watch reads 2, and that is correct** — it has two IMAP triggers, Sent Folder and Inbox (verified 2026-09-16).

**These signals prove a publish happened, not that the triggers are connected now.** When a running trigger fails — an IMAP socket closed by the server, say — n8n drops *all* of that workflow's triggers from memory, records an activation error, queues a reactivation, and writes nothing to the database: `active`, `activeVersionId`, `triggerCount` and the publish-history row stay exactly as they were while the workflow listens to nothing. The reactivation retries forever, but the wait starts at 1 s and doubles after each failed attempt up to a **24-hour cap** (`WORKFLOW_REACTIVATE_MAX_TIMEOUT`), so after an outage of a few hours the next attempt can be roughly as far away again — the trigger stays down after the far end is back. Only a `mode='trigger'` execution after the failure, or the log line `Activation of workflow "…" was successful!`, shows it recovered. What this has done in practice is recorded under Workflow 6.

**n8n execute against an already-running container needs runner env overrides.** A one-off `docker exec ... n8n execute --id=...` against the live container conflicts with the main process's own task-runner broker unless you pass `-e N8N_RUNNERS_BROKER_PORT=5690 -e N8N_RUNNERS_ENABLED=false`. Without these it can hang or fail confusingly.

**Verify before building anything on top:** run `ollama ps` after loading and confirm the model shows 100% GPU, not a CPU/GPU split.

**Escape hatch — TAKEN 2026-10-02 (drafting skill v3).** The plan was to swap only the drafting node to the API if local drafts needed heavy editing after two weeks of real use. It was taken on a design reason instead: composition needs a frontier model, and line-picking was what kept the 9B safe. Only the drafting node moved, to Sonnet 5.5 rather than Sonnet 5; the follow-up composer joined it the same day (it is low-volume too: at most two per emailed lead). Enrichment and scoring stay local permanently — those are the high-volume nodes.

**Message rules — LOCKED:**

## 7. Pipeline Architecture

Six workflows, each independent, each queue-driven.

**Correction — the original assumption here was wrong.** "Conserve Apollo credits by scoring first" assumed the constraint was volume/rate. Measured directly: Apollo's Free plan returns 403 API_INACCESSIBLE on `mixed_people/search`, `people/match`, and `mixed_companies/search` regardless of credit balance — the account showed 125 unused credits throughout and consumed zero. Credits shown in Apollo's dashboard are a UI allowance, not an API entitlement; the gate is the plan tier, not usage. Pipeline order still controls volume, but volume was never the actual constraint.

**Decision: don't upgrade Apollo.** 5 of the first 9 qualifying leads were satisfiable for free from data already scraped (ICH GCP profile pages carry an email field the original `leads` table schema had no column for — recovered and used directly, no API call). The remaining gap is genuinely small — a few leads at a time with no scraped email — and fits the existing human-review design better than a paid integration would: when a qualifying lead has no contact, that's a two-minute manual look-up in the review queue, not something worth paying to automate at this volume. Revisit only if that gap grows large enough to actually be a burden.

**Critical ordering rule (still correct, for a different reason):** Apollo contact lookup happens AFTER scoring, never before — this controls volume and avoids wasted lookups on leads that get disqualified, even though it turned out not to be what "kept" Apollo free.

**Idempotency rule — LOCKED:** the host machine will be off some of the time. No workflow may assume its schedule fired. **Correction to the 2026-10-02 root cause, which was right about the bug and wrong about one detail.** That entry says "minutes intervals are counted on elapsed time in that function and are safe" and treats every `hours` rule as unsafe. Read from the installed `GenericFunctions.js` on 2026-10-07: `intervalToRecurrence` activates **no** recurrence check at all for `hoursInterval === 1` (nor for `days`/1, `weeks`/1), so an hourly rule has no clock-value gate and fires every hour at a stable minute. `recurrenceCheck`'s minutes branch now uses an **absolute** minute count (`Math.floor(now/60000)`), not the 0–59 wall-clock value, with a comment saying so — so minutes are safe for a stronger reason than elapsed-time counting. The hours branch still compares `momentTz.hour()`, so `hours` **above 1** remains unsafe exactly as recorded, which is what cost the three follow-ups. Contact Lookup's `hours`/1 therefore needs no change, and did not get one.

**And the other half of the rule, which no guard had covered: a fixed slot.** An interval of 1 passes the clock-value test and can still have exactly one moment a day to fire in, because `triggerAtHour` pins the cron's hour. That is precisely what Ingestion was. Every generator now refuses, at build time, any schedule that is `hours`/`days`/`weeks` above 1 **or** that pins `triggerAtHour`, `triggerAtDay`, `triggerAtDayOfMonth` or `triggerAtMinute` — `n8n/{ingestion,contacts,enrichment,scoring,drafting,sendtrack}/build_workflow.py`, with cases in the ingestion, contacts and sendtrack drift-guard suites proving each refusal fires.

**A workflow whose input is a file, not a queue, needs a different answer.** Ingestion is the only one, and the fix is in kind rather than in cadence: it ticks every 30 minutes like its neighbours and does its work when the committed CSV has changed since the last ingest (`ingest_log`, migration `015`; Section 9, Workflow 1). A quiet tick is one HTTP GET and one `SELECT`. The Daily Digest is the other workflow with a time of day in it, and it is already built this way — the hour is a floor, not a slot, and a day the host was never up at or after it folds into the next digest instead of vanishing. That is now pinned by tests rather than only by reading: a host coming up at 10:40, or at 23:00, still sends that day; a second tick does not send again; and a three-day window comes out as one email.

**What none of this fixes.** When the host or Docker is down, nothing inside the stack runs, including the health check — the open item is Docker Desktop's `AutoStart`, still `false` (Section 13). The schedules now guarantee that whenever the stack *is* up, every stage has work it can pick up, rather than needing to have been up at a particular minute.

## 9. Workflow Specifications

### Workflow 1 — Ingestion
**Trigger:** Cron, every 30 minutes, doing its work only when the committed CSV has changed since the last ingest (migration `015`) — daily 23:00 Asia/Karachi until 2026-10-07, weekly until 2026-10-06; see "Ingestion runs when the file has changed" and "Expansion beyond the core 13" below. The GitHub Action that feeds it runs one region per weekday.
**Sources:**
- ICH GCP directory (`ichgcp.net/cro-list`) — per-country pages, server-rendered, no JS needed.
- Manual CSV import path for referrals and conference lists — via psql `COPY`, no workflow needed yet.

**ICH GCP page structure — VERIFIED, two-stage scrape required:**

Country pages (`/cro-list/country/{slug}`) list companies with name, truncated description, and a link to an ichgcp company profile page — but **no external website URL**. The CRO's actual domain appears only on the company profile page (`/cro-list/country/{slug}/company/{company_slug}`) as a `Web:` field. Exception: the two paid "Featured CROs" slots at the top of each country page do carry a direct website link.

So: stage 1 collects profile URLs from the country page, stage 2 fetches each profile to extract the domain. Budget ~15–40 profile fetches per country. Rate-limit politely.

**ICP pre-filter — free, use it:** each country page splits listings under two headings, "Local, small- and mid-size Contract Research Organizations in {country}" and "Global Contract Research Organizations in {country}". The global section is IQVIA, ICON, Parexel, PPD, Syneos, SGS, Fortrea et al — all of which the Section 9 disqualifiers reject on employee count anyway. **Scrape only the local/mid-size section.** Halves fetch volume and pre-qualifies leads before any enrichment spend.

**Access — confirmed IP-level block, not a UA block.** ichgcp.net returns 403 from the dev machine even with a full browser User-Agent spoofed — the block is IP/GeoIP-based, not a `curl` signature match. n8n running locally cannot reach this domain at all, now or on a weekly schedule.

**Shipped architecture:** the scraper runs as a scheduled GitHub Action (`.github/workflows/scrape-ichgcp.yml`, weekly + manual dispatch) from GitHub's runners, and commits `data/ichgcp_leads.csv` to the repo only when it changes. The local n8n workflow (`n8n/workflows/ingestion-ichgcp.json`) never touches ichgcp.net — it fetches the committed CSV from `raw.githubusercontent.com` and upserts into `leads`. This cleanly separates the blocked scrape from the pipeline.

**Known risk, unresolved as of first build:** GitHub Actions runner IPs are datacenter-class and commonly penalized by the same reputation-based WAF systems that block scraping traffic generally — there is a real chance the Action itself also gets 403'd on first run, independent of UA string. If so, the next lever is a small always-on VPS with a residential-leaning IP, or a scraping proxy service — not a scraper redesign, the parsing logic itself is already fixture-tested and sound.

Scraper UA: self-identifying (`NovaScoutBot/1.0` + repo link), not a spoofed browser string — deliberate choice, overridable via `ICHGCP_USER_AGENT` env var if needed.

**Sprint 1 outcome, validated end-to-end and closed:** no 403s across two full Action runs — the IP-reputation WAF risk did not materialize. Only 429 (rate limit) and 404 seen. Remaining profile-fetch failures (4) are genuine dead links on ichgcp.net's side — correctly left non-retryable.

**Known, accepted limitation — corrected mechanism.** The shipped upsert is `ON CONFLICT (domain) DO UPDATE`, not `DO NOTHING` as originally assumed here. For a multi-country CRO (same domain on several country pages), this means **the last-processed country in a given ingestion run wins `leads.country`, and it can flip on every re-run** — observed directly: `bitrial.hu` flipped Romania→Poland when the CSV was re-ingested with Poland's leads included. `status` is excluded from the update, so this never regresses pipeline progress (verified in Sprint 1) — only `country` (and other metadata) is unstable.

**Why this doesn't currently hurt scoring:** the scraper only ever touches the 13 target-geography countries, so a flip can only ever land on another already-target country — Section 9's 25-point geography weight is scored identically either way. This would stop being true if the source-country list and target-geography list ever diverge. Not urgent; the fix, if it's ever needed, is the same `lead_countries` join table already noted for the undercounting issue below — one fix resolves both. **They diverged on 2026-10-06** (every directory country is now a source, only 13 are core, and the geography factor is worth 10 for a core country and 5 for any other): a CRO listed in Mexico and Germany would have scored 10 or 5 depending on which country the last run happened to process. The fix did not need the join table — the scraper's merge now keeps one country per domain by a fixed rule (core beats extended; otherwise the row already there wins), so the CSV's country, and therefore `leads.country`, is stable across runs. See "Expansion beyond the core 13" below.

**Known, accepted limitation, undercounting:** the same domain-collision dedup means some countries' raw per-scrape totals don't match what lands in the DB (observed: Hungary 8→6, UAE 3→2). Correct behavior for avoiding duplicate lead rows; accepted as-is at current scale (~3% of leads affected).

- **Discovery is live.** Each run reads `/cro-list` and takes every `/cro-list/country/{slug}` link on it. - **What "changed" means:** a fingerprint of the three columns the upsert writes — domain (normalised, the dedupe key), company name, country — canonicalised, sorted by domain, hashed with FNV-1a/64 in BigInt, with the row count carried alongside it (`fnv1a64:<16 hex>:<rows>`). A rewritten description, a new phone number or a changed address is a real change to the file and no change at all to `leads`, so it does not trigger an ingest; the e-mail column is out too, because Workflow 3b re-fetches the CSV and reads that itself. The build refuses if the hashed columns and the upserted columns ever differ — a column in the hash and not the upsert means pointless re-ingests, and one in the upsert and not the hash means a real change to it is **never** ingested, which is the silent failure.
- **Not a cryptographic hash, on purpose.** The Code sandbox refuses `require('crypto')` (measured 2026-10-07: "Module 'crypto' is disallowed") and has no `crypto.subtle`; BigInt, Buffer and TextEncoder are there. Nobody is forging a collision against a file we publish ourselves, and a collision would have to preserve the row count exactly as well.
- **Recorded after the upsert, never before.** A crash in between leaves the fingerprint unrecorded and the next tick redoes the whole thing, which is free because the upsert is idempotent; recorded first, a crash would mark a file ingested that never was. `ingest_log` keeps `leads_before`/`leads_after`, so each row says what that ingest actually added — the number this document used to record by hand.
- **A file that parses to zero rows is not a new version of anything.** `raw.githubusercontent` serving an error page, or a scrape that wrote nothing, is refused by the same gate, so it cannot record an ingest.
- **This stage got a generator** (`n8n/ingestion/build_workflow.py`) with the schedule change — it was the last one still hand-written, and the change added two Code nodes whose JS has to be the same text the tests run. The guards: the trigger may not be a fixed slot or a clock-value-gated interval, the upsert may not write a column Section 8 does not define and **may never set `status`** (at a 30-minute tick that would drag every lead in the file back to `ingested` twice an hour), the record may not write an unknown `ingest_log` column, and every `$json.X` a node reads must be emitted by the node above it — Workflow 4's silent-empty-field class of bug, which here would have upserted 272 blank rows and reported success. `n8n/ingestion/test_drift_guards.py` (17 cases) proves each one fires; `test_fingerprint.js` covers the hash and the fan-out.

### Workflow 1b — Ingestion: research sites and SMOs from Trialsites (2026-10-09)

**Why a second source.** On 2026-10-09 the CRO pipeline had run dry: 506 leads, none waiting at `ingested`, `enriched` or `contact_found`, the contact-lookup queue empty (all 11 leads at ≥ 50 already retired to `needs_manual_contact`), and **15 approved, unsent first touches — 0.75 days of supply at the 20/day ceiling**. Independent clinical research sites and site management organisations (SMOs) hear from the same visitors a CRO does — sponsors — and also from CROs choosing sites for a study, so they are the next market for the same product. `trialsites0001` (`n8n/workflows/trialsites.json`, generated by `n8n/sites/build_workflow.py`; migration `019`).

**The source: Trialsites, the AIMR Global Clinical Research Site Database** (`trialsites.aimronline.org`; API `https://api.aimronline.org/api/v1`). Read from its API page on 2026-10-09: read-only JSON, **no authentication, 60 requests per 60 seconds per IP**, 142,889 sites in 237 countries aggregated from 14 public registries (CT.gov, CTRI, ISRCTN, ANZCTR, EU CTIS, …), tiers A 14,757 / B 28,483 / C 40,419 / D 54,502. **The same page says "Free for non-commercial use"** — Nova Scout is commercial outreach, so that is an operator decision before this workflow is published (Section 13). Endpoints: `/sites` (search, filters `country`, `tier`, `ta`, `has_ta`, `facility_type`, `regulator`, `network`, `min_trials`, `identified_only`, `active_only`, `q`, `sort`, `limit` ≤ 500, `offset`), `/sites/{location_id}` (detail), `/countries`, `/regulators`, `/therapeutic-areas`, `/stats`. **The site object's fields:** `location_id`, `canonical_name`, `city`, `state`, `country`, `latitude`, `longitude`, `geo_precision`, `trial_count`, `active_recruiting`, `recent_trials_3yr` (multi-registry aggregates), `top_conditions`, `therapeutic_areas`, `primary_ta`, `top_sponsors`, `investigator_count`, `total_enrollment`, `avg_enrollment`, `network_name`, `network_type`, `facility_type`, `regulatory_authority`, `external_uuid`, `external_rank_global`, `external_rank_country`, `external_nct_count_est`, `quality_score` (0–1), `site_tier` (A–D), `site_identification` (`identified` / `partial` / `area_only`), `data_sources`. **There is no website, domain, e-mail or phone field** — that is why step 2 exists. The detail endpoint adds `external_links` and investigator records; **this workflow never calls it**, no column could hold what it returns, and the build refuses a Code node that reads investigator fields (the standing rule: never use personal investigator e-mails from registry data).

**Lane 1 — the weekly harvest** (`code_harvest_requests.js`, `code_select_candidates.js`). Every 30-minute tick asks `site_harvest_log` whether a harvest ran in the last 7 days — a question about the table, not about a clock, so a host that was off on harvest day harvests at its next tick (Section 7). When due: read `/countries` live (Trialsites spells some countries two ways — "Czech Republic" and "Czechia", "United States" and "United States Of America" — and a request for one misses the other's rows), map each spelling through an explicit alias table to Section 12's clock table (**only countries the ICH GCP scraper already includes**; the build refuses an alias that targets anything else, so a sanctioned jurisdiction cannot be reached), then for every mapped spelling and tier A and B request `/sites?identified_only=1&sort=-recent_trials_3yr&limit=500`, up to 4 pages — **strictly one request in flight at a time**: `Loop Over Requests` (n8n's Loop Over Items, batch 1) hands the HTTP node one country/tier, its pages follow one after another 1.1 s apart, and `Pace Requests` waits 1.1 s before the next. The first build used the HTTP node's own batching instead and the dry run caught it: that option only sleeps between dispatches and never awaits a response (the Workflow 4 caching probe found the same in the installed source), so slow answers overlapped with each other and with extra pages, and **8 requests timed out at 60 s in a harvest's first four minutes** (4 still failed after retries). The build now refuses batching on that node and refuses it outside the loop. Selection is deterministic (build rule 3), first failing rule wins so the tally adds up: included country → tier A/B → `identified` → **active** (≥ 1 trial in the last three years or ≥ 1 recruiting now) → not an institution by type (`University Hospital`, `Children's Hospital`, `Government/Military Hospital`, `Community Hospital`; networks `Academic Medical Center`, `Hospital System`, `Government`) → not an institution by name (hospital, university, faculty, ministry, national, state, federal, NHS, trust, military, IMSS, … in the included countries' languages, whole words of the accent-folded name) → a **positive signal** (a research word in the name, a company legal form at its end, or `Private Practice` / `CRO / Phase 1 Unit` as its type). The positive signal is required because `facility_type` is empty on 88 % of tier A/B rows (measured on 5,145 rows across eight countries) and a public institution is far commoner in this data than an independent site; a lookup costs money, so a name with no signal is not a candidate. Then: not already a candidate (`location_id`), one per name + city, ordered core country first, then tier A, then recent and lifetime trials — and **at most 200 new candidates a week**. Candidates and the harvest's log row are written in one statement.

**Lane 2 — the website lookup** (`code_build_lookup.js`, `code_verify_site.js`). A batch of at most 10 candidates per tick, never more than the month's remaining cap divided by the worst case of one lookup ($0.04), so a batch is never sized past the cap. **The model proposes, code decides.** Claude Haiku 5.5 with server-side web search (Section 4 has the measurement that chose it) gets the name, city and country Trialsites published — nothing else — and answers `{url, evidence_url, confidence}` against a strict schema. Code then refuses a directory, social network or registry, an institutional domain (`.edu`, `.gov`, `.ac.xx`, `.nhs.uk`, …) and a sanctioned ccTLD (Section 12's row-level screen), fetches the homepage (the same https/http/www rungs as Workflow 2), the model's evidence page and up to three contact/location pages on the same host, and **accepts the site only if the candidate's name and its city both appear in that text**. No confident match is a skip, never a guess. Whether the host was in the search results is recorded (`from_search`), not required: the fetch is the confirmation, and a page that names this organisation in this city is the right site however the model learned its address. Outcomes: `resolved` (a lead is written), `duplicate` (the domain is already a lead — an ICH GCP CRO or another location of the same network — and that lead is never touched), `no-match`, `not-confirmed`, `excluded`, `call-failed` (retried up to 3 attempts; every other outcome is final, because a second paid lookup of the same name has no reason to answer differently). The outcome, the lead and the cost are recorded in one statement, so a crash cannot leave a lead whose candidate still reads `pending` and is paid for again. A resolved site becomes `leads (domain, company_name, country, source='trialsites', status='ingested')` and from there is an ordinary lead: Enrichment, Scoring, Contact Lookup, Drafting.

**Contacts for a site lead come only from its own website.** Trialsites carries no address, so Workflow 3b's order applies unchanged: the committed ICH GCP CSV has nothing for these domains, so the first source that can answer is an address **published on the lead's own site, same domain or a subdomain, never pattern-derived** (`code_site_emails.js`), then a founder LinkedIn, then Apollo (plan-gated, so in practice `needs_manual_contact`). Registry investigator data is never a source.

**Execution data:** a harvest carries ~30–40K rows, so `trialsites0001` saves no successful execution data (failures are kept); every outcome and every cent is already in `site_candidates`, `site_lookup_log` and `site_harvest_log`.

### Workflow 2 — Enrichment
**Trigger:** Cron, every 30 min. Batch of 10 where `status='ingested'`.
**Steps:**
1. Fetch homepage, /about, /services, /team via HTTP node
2. **Chatbot detection is a Code node with regex — NOT an LLM call.** Match against known widget scripts: Intercom, Drift, Tidio, Tawk, Crisp, HubSpot chat, LiveChat, Zendesk. Never spend tokens on what a string match answers.
3. Ollama node with `format: json` and explicit schema → therapeutic areas, phases, founder, employee estimate, site notes
4. Write to `enrichments`, advance status

**`company_type` replaced `is_cro` — 2026-10-09.** With research sites and SMOs a second lead source (Workflow 1b), a boolean "is this a CRO" could not say what a lead is. The schema now asks for `company_type` as a closed enum — `CRO`, `site`, `SMO`, `other`, `unclear` — with a one-line definition of each in the prompt (a CRO that also runs its own phase I unit is still `CRO`; a private practice that runs trials is `site`; a hospital, university, government body, agency, consultancy, vendor, supplier or pharma company is `other`), so the grammar enforces it the way it does the taxonomy, and `code_normalise.js` maps anything else to null. `build_workflow.py` parses the list out of Workflow 3's disqualifier sentence and refuses to build if the schema, the normaliser or this document disagree. Rows enriched before that day keep their `is_cro` and free-text label and are **not** re-enriched; Scoring reads the old fields for them alone. Drafting and the reply path read the type through `lead_company_type()` (migration `019`, Section 8): enrichment's answer when it is `CRO`, `site` or `SMO`, otherwise the source (ICH GCP → CRO, Trialsites → site).

### Workflow 3 — Scoring
**Trigger:** Cron. Batch where `status='enriched'`.

**Hard disqualifiers (deterministic Code node, runs first):**
- Already has a chatbot
- Employee estimate > 500 (enterprise CRO) — **only on a confirmed number.** Real Sprint 2 data: `employee_estimate` is null on 85% of leads (sites rarely state headcount, and extraction correctly refuses to guess). Null must never trigger this disqualifier — treat it as unknown, not as evidence of scale. Same null-safe handling applies to `founder_name`/`founder_linkedin`, sparse for the same honest-refusal-to-guess reason.
- No functioning website — **"unreachable" over-counts; investigation closed, accepted at current scale.** Of 26 originally flagged, 7 were alive. 2 rescued by relaxing TLS cert validation (broken/mismatched certs, not a block — one, `gvkbio.com`, is a 3,412-employee CRDMO that will correctly hard-disqualify on employee count once Sprint 3 runs). The remaining 5 end in HTTP 403 on every retry rung regardless of technique — confirmed WAF blocks, same class as ichgcp.net, genuinely up but hostile to non-browser clients. Not worth extending the GitHub-Actions-IP workaround here — that was justified for ichgcp.net as the sole ingestion source; for ~5% of individual enriched leads it isn't. Accepted as a permanent, expected loss rate.

  **Design implication for this disqualifier specifically:** don't treat "unreachable" as instantly and permanently disqualifying. Give a lead a bounded number of enrichment attempts (e.g. 2) before trusting the marker, and treat a confirmed WAF-block (got an HTTP 4xx response) as weaker evidence of "no functioning website" than a true connection failure — a 403 proves the site exists. Not yet implemented; decide the exact mechanism when this workflow is actually built.
- Not a CRO, site or SMO (agency, consultancy, vendor, hospital, university, government body) — **changed 2026-10-09** from "not actually a CRO", when research sites and SMOs became a second lead source (Workflow 1b). Enrichment now classifies `company_type` as exactly one of `CRO`, `site`, `SMO`, `other` or `unclear` (a closed enum in the Ollama schema, so the grammar enforces it); only `other` disqualifies, and `unclear` or a missing value never does (null is not evidence). A lead enriched before that day carries the old boolean `is_cro` and a free-text label instead; for it the rule fires on `is_cro = false` unless the label itself says site or SMO.
- Domain on blocklist

**Weighted fit score (0–100):**
| Factor | Weight |
|---|---|
| Target geography | 10 |
| Active trials on ClinicalTrials.gov | 20 |
| Founder/MD identified with LinkedIn | 20 |
| Oncology focus (strongest case study) | 15 |
| Employee count 5–100 | 25 |
| Site quality suggests budget | 10 |

**Geography is three-tier since 2026-10-06 (Section 12), and since 2026-10-07 every included country also has a business-hours clock, so a tier-2 lead is now genuinely sendable rather than scored and stranded.** The 10 is the ceiling: a lead in one of the 13 core geographies earns all of it, a lead in any other country the directory lists earns 5, and a lead with no country, or in an excluded jurisdiction, earns 0. The weight itself is unchanged, so every other number in this section stands. `fit_score = 0` still means *disqualified*; an excluded country is deliberately **not** a hard disqualifier here, because the scraper never lets one into the CSV and Send holds any country without a business-hours clock — see Section 13 if a sanctioned lead could ever be imported by hand.

**Active trials for a Trialsites lead — 2026-10-09.** For a CRO the 20-point "active trials" factor is a ClinicalTrials.gov sponsor-name match, which hits about 8 % of the time because a CRO is a trial's collaborator, not its sponsor (below). For a research site or SMO found through Trialsites (Workflow 1b) the factor measures something real: Trialsites aggregates 14 registries per **location**, so its counts are trials actually run at that site. A lead with a linked `site_candidates` row (one written by Workflow 1b, `source = 'trialsites'`) therefore takes this factor from Trialsites instead, and the ClinicalTrials.gov answer is not used for it — not even its failure, so a CT.gov outage does not hold a site lead back. The three components sum to the factor's full weight; each takes the highest band the lead reaches:

| Trialsites component | At least | Points |
|---|---:|---:|
| recent_trials_3yr | 10 | 10 |
| recent_trials_3yr | 5 | 7 |
| recent_trials_3yr | 2 | 4 |
| recent_trials_3yr | 1 | 2 |
| trial_count | 50 | 5 |
| trial_count | 20 | 4 |
| trial_count | 10 | 3 |
| trial_count | 5 | 2 |
| trial_count | 1 | 1 |
| site_tier | A | 5 |
| site_tier | B | 3 |

**Why these weights.** Recency carries half the factor because a site that started ten or more trials in the last three years is fielding sponsor and CRO inquiries *now*, which is the traffic Nova answers; an old track record with nothing recent is the weaker signal. Lifetime volume (`trial_count`, all registries) is a quarter: experience, but it says less about this year. Tier is AIMR's own quality tier (A/B only — Workflow 1b never selects C or D), a quarter, worth only 2 points between A and B because it grades the record's completeness as much as the site. The floor for a candidate is 4 (tier B, one trial ever, recruiting but nothing started in three years); a busy tier-A site with ten recent and fifty lifetime trials earns all 20. If a domain has several Trialsites locations (a network), the strongest one counts — never a sum, which would score a network's size rather than one site's activity. `n8n/scoring/build_workflow.py` parses this table, refuses a build where the top bands do not add up to the factor's weight, and checks `code_evaluate.js` carries the same bands.

**Rebalanced from the original 25/20/20/15/10/10, based on real Sprint 3 measurement, not upfront guessing.** Geography scored 25/25 for all 79 scored leads with zero variance — the only ingestion source (ICH GCP) is already filtered to the 13 target countries, so this factor measures "did our scraper touch this lead," not fit. Kept nonzero rather than dropped to zero, as cheap insurance against a future non-pre-filtered source. The freed 15 points went to employee count: real data showed a company far outside the 5–100 band (~300 employees) ranking #1 overall despite the scoring rationale itself flagging the mismatch as disqualifying in substance — the old 10-point weight didn't cost enough to matter against strong scores elsewhere. This does not change the separate >500 hard disqualifier, which stays as-is.

**ClinicalTrials.gov — measured, not assumed.** The originally-specified `query.locn` country-only fallback was never implemented: measured directly, a bare country search returns 600+ recruiting trials for India alone, which would have awarded the full 20 points to nearly every lead — the same non-discrimination problem geography had, just undetected before shipping. Only the primary `query.spons` sponsor-name lookup shipped (real ~8% hit rate — CROs are usually a trial's collaborator, not its registered sponsor).

Test `query.term` against exactly this 18-lead set first, with the same false-positive scrutiny that killed the sponsor-name-cleaning idea, before shipping or discarding it. **That condition was met on 2026-09-06 (the next paragraph: `query.term` tested and rejected), and the threshold was then lowered on 2026-10-06 for exactly the reason this paragraph held it back — see "Decision 2026-10-06" below.**

| Company | totalCount | What actually matched (sampled) |

The measurement is what the 2026-10-06 decision below rests on: with no fairer query available, the threshold was lowered rather than the factor "fixed".)*

**Null-handling for weighted factors:** where `employee_estimate` or `founder_name`/`founder_linkedin` is null, that factor contributes a neutral partial score, not zero — a confirmed miss (e.g. a named founder found and clearly not on LinkedIn) should score lower than an honest unknown. Don't let extraction's correct refusal to guess become a scoring penalty.

**Implemented and verified** in the enrichment workflow — grammar-constrained, drift-checked against `code_normalise.js`, adversarial-tested (zero off-enum output). **Known, accepted, unrelated:** non-English source text doesn't reliably map into the `phases` field — e.g. Turkish `biyoeşdeğerlik` didn't resolve to `Bioequivalence`. Real gap, low priority, not touched.

**ClinicalTrials.gov lookup mechanism (this is where that source lives):** for each candidate that has cleared hard disqualifiers, call `GET https://clinicaltrials.gov/api/v2/studies` with `query.spons=<company_name>` (and `query.locn=<country>` as a fallback if the sponsor-name search misses) and `filter.overallStatus=RECRUITING`. **A third free source, and the queue stops starving — 2026-10-07 (migration `015`).**

**The starvation, measured.** The queue is `status='scored' AND fit_score >= 50 AND no contacts row`, ordered `fit_score DESC` and capped at 10. A lead with no scraped address and no founder LinkedIn went to Apollo, was refused (403, plan-gated), wrote nothing, stayed `scored` — and came back at the **top** of the next hour's batch, because it scores well. Nine leads were in that state on 2026-10-07: 35, 53, 92, 94, 212 (the five Section 13 already named) plus 498 Austria, 500 Belgium, 658 Netherlands and 733 United Kingdom, all from the europe shard. At ten, the batch of 10 would have held nothing but stuck leads and no new lead would ever have been looked up again. The queue had no memory of a lookup that found nothing, and `contacts` had nowhere to keep one: a tombstone row there means "asked, nobody there", which is a different thing from "asked, Apollo would not answer", and Section 8 locks that table's columns.

**The fix is `contact_attempts` plus one clause.** Two ways out of the queue, and the second is the one that cannot be defeated. `last_outcome = 'exhausted'` retires a lead whose every source has genuinely answered — and that now includes the plan-gated 403, because it is a property of this account and will answer identically every hour until somebody upgrades; `attempts >= 3` retires one whose refusal nobody recognised, so an unfamiliar error shape costs three ticks rather than the queue. The classification is positive-recognition only (`isPlanGate` in `code_pick_contact.js`): a 429, a 5xx, a timeout or an unparseable response is still `refused` and still retried, so "a refusal is not evidence" holds for every refusal that could pass next time. A lead retired by the count alone shows `last_outcome = 'refused'` in the view, which is the signal that the recogniser needs a new case rather than the lead needing a human. The lead stays `scored` throughout; a lookup that **does** find a contact deletes the record in the same statement that writes the contact, so a lead since reached leaves the manual queue. **Delete a row to re-queue a lead** — the move to make after an Apollo plan upgrade, alongside deleting the LinkedIn-only contacts above.

**The new source: an address the company publishes on its own website** (`Harvest Site Emails`, `n8n/contacts/code_site_emails.js`). Three rules, each earning its place against a real page:

- **Nothing is pattern-derived.** No `first.last@`, no `info@<domain>` on the grounds that most companies have one. A guessed address is a different kind of thing from a published one, and that is exactly the line `contacts.verified` draws (above, and `n8n/contacts/README.md`). An obfuscated address ("info [at] example [dot] com") is not un-obfuscated either, because that is a guess about what the page meant.
- **The lead's own domain, or a subdomain of it.** `mtz-clinical.pl` publishes only `@pratia.com` addresses (it was acquired), `cebisinternational.com` only `@cebis-int.com`, and `archerresearch.eu` only Wix's `@sentry.wixpress.com` telemetry. All three are the wrong company or no company, and all three are rejected by this one rule — which is three of the four leads this source could not help.

Where a page offers several, a deny list decides what is usable and a short preference ladder decides between what is left — business development before a general inbox before an operational one — except that a mailbox carrying the founder's own name wins outright, because two independent sources then agree on the person (the same corroboration the Apollo ranker uses). Ties break by length then alphabetically, so two runs of one batch write the same address. An address found here is written **`verified = true`**: it is a first-party address the company published about itself, which is the same ground the ichgcp profile address stands on. A scraped address still beats a site one — the CSV is a committed file, so it is the same address on every run for ever, while a site is whatever it serves today.

So the stage that needs an address goes and looks for one, which also means it reads the site as it is today rather than as it was when the lead was enriched. At most five requests per lead, only for leads with no address on disk, only on the lead's own host, three leads at a time: a batch of 10 is at most ~50 requests across as many hosts.

**Trigger:** Cron. Batch where `status='contact_found'`.

**Grounding guard — LOCKED.** The drafting prompt may only use facts present in the enrichment record. If the record lacks at least two specific facts (therapeutic area, named trial, city, founder name), the draft is flagged `low-context` and skipped rather than invented.

> This rule exists because of the Nova field-fabrication bug: under forced tool use, Haiku invented a specialty from an email domain. Small models fabricate when under-informed. Design for it.

**Refinement, found in Sprint 4 testing: the failure mode isn't only fabrication, it's joining.** A sentence can use zero invented words and still assert an untrue relationship — "one recruiting oncology trial in Istanbul" traces to two real, separate facts that were never actually linked. Word-level grounding passes this; claim-level grounding doesn't. Lowering temperature (0.7→0.45) reduced fabrication but did not fix joining — that needed prompt structure, not sampling: attach an explicit boundary to each fact rather than listing them freely, cap therapeutic areas mentioned at two (five read as generic, not specific), use second-person trial phrasing (third-person produced "their own material" — an odd distancing artifact), and bar `founder_name`/`city` from the opening line specifically — allowing it produced "Enrique Gaubeca is founder or MD on their site" as the first line of a LinkedIn DM addressed to Enrique Gaubeca.

**A silent wiring failure, not a logic bug — check for this class of thing whenever a node chain is edited.** The first live run reported `"status": "success"` on all four drafts, and every one of them mentioned neither Nova nor NoblePath. The system prompt was set correctly on the Config node, but a later Postgres node in the same chain replaces the item outright rather than merging into it, so `$json.system_prompt` was an empty string by the time the Ollama call read it — the model drafted with no instructions at all, silently, no error anywhere. Unit tests validate logic given correct inputs; they cannot see wiring, and runtime doesn't error on a field that's simply absent. Fixed with a build-time guard: every `$json.X` field the Ollama body reads must be traceable to something `code_assess.js` actually emits, checked at build time, not assumed from the node graph looking right.

**Prompt constraints (skill v3):** body 70–110 words, never more than 125; minimum two specific facts, one geography-matched live customer (drafting skill v2; this replaced "mention the live NoblePath demo"), no adjectives like "revolutionary" or "cutting-edge", no merge-tag phrasing tells.

**Drafting skill v2 — shipped 2026-09-19 (`NovaScout_DraftingSkill.md`).** The grounding guard above is unchanged. It still counts the same four facts against the same threshold, the fact sheet and its boundary sentences are the same, and the v1 grounding tests pass untouched. What changed is what the model is asked to write. It now writes **a subject and two one-sentence hooks, and nothing else**. Its JSON schema has no other field, and the build refuses a schema that disagrees with the skill's "only the hook and subject are freely generated". The problem, outcome, proof and exactly one ask are `claims_library` lines (Section 8, migration `010`), inserted verbatim after the hook. They are rotated on `lead_id` and chosen to fit the ceiling. The model never sees them, so it cannot paraphrase a claim or join a fact onto one. A draft's `variant` records the line codes (`role-inbox/P2.O2.PR-MX.A2`), which is what the learning loop needs to tell which lines earn replies. Per skill §2 the 80-word ceiling counts the body, parts 1–5; greeting, opt-out and signature are outside it (v1 counted the opt-out).
- **Proof is geography-aware** (Section 12), resolved from each proof line's `countries`. A groundable lead the library cannot complete waits at `contact_found` rather than go out with a hole in it.
- **Links:** none in warm-up weeks 1–2, where the week is derived exactly as Workflow 6 derives it. After that the only URL allowed is the library's `link` line. A LinkedIn URL or a PDF is tagged in any week.
- **Subject:** 30–50 characters, never "Nova", never "Re:"/"Fwd:", none of the skill's banned words. It is generated with a worked-example table in the system prompt and built from the same fact the email opens with. A small confirmed headcount (Section 12's 5–100 band) is used only for the subject, and only when no openable fact exists. It never counts toward the guard.
- **Leaks from the worked examples are caught deterministically.** A digit token that is not in the lead's facts, or a therapeutic area the lead lacks, tags the hook or subject `-ungrounded`. Measured before the fix: a trial with no drug code got "INM004 trial — a quick question". Picking the trial's short name moved into code: its code, otherwise the first two content words of the title. Also measured: a hook nudged to vary its wording wrote "Your site lists work on the Efficacy of INM004…" — every word traces to the record, and the sentence is still untrue, because the trial is on ClinicalTrials.gov, not their site. That hook-vs-source failure is now tagged `hook-source`.
- **A redraft retires what it replaces.** A lead sent back to `contact_found` has its earlier pending or approved first-touch drafts set to `rejected` / `bad draft`, in the same statement that writes the new ones. Left approved, the old draft would be the first thing Workflow 6 sends, since it sends the oldest approved draft once a lead is `drafted` again. New drafts are always `pending`, bodies and `edited_body` are kept, and sent drafts and follow-ups are never touched.
- **Terminology — decided 2026-09-21: the pharma-side party is a "pharma team", and "sponsor" belongs to the CRO.** A trial hook opens "You're sponsoring …", the prospect as the registered sponsor of its own trial, so a library line that also said "sponsor" for the pharma company put one word on two parties in the same email. Measured on the queue that day: all 5 drafts that opened "You're sponsoring" then used a library line saying "sponsor" for the pharma side. What a CRO reads now says "pharma team" (noun) or "pharma-team" (modifier): `claims_library` P1–P3, O2 and O3; the subject worked example in the system prompt and in skill §3 (`Pharma-team inquiries after hours`; a lead whose subject source is `problem` is steered to it, so it decides a real subject line); and `nova-one-pager.docx`. "Sponsor" stays only for the CRO's own registered-sponsor status. **Prompt caching, and the batch split that was built and then rejected — 2026-10-08.** Section 3 has the settings and Section 4 the money. What belongs here is the one design decision that did not go the obvious way, because the reasoning is reusable and the failure mode is the dangerous kind.

The problem is real and was already recorded: n8n's HTTP Request node starts every item's request inside its item loop and awaits them all afterwards — read from the installed `HttpRequestV3.node.js`, `requestPromises.push(...)` inside `for (let itemIndex ...)` then one `Promise.allSettled` — so a batch's calls are concurrent, and a cache entry is readable only once the response writing it has begun. Four concurrent calls on 2026-10-02 wrote the cache four times and read it never. **The node's own `batchSize`/`batchInterval` options do not fix this**: the same source shows they only `await sleep(batchInterval)` between dispatches, never waiting for a response. So the fix has to be structural — the batch's first lead calls alone, the rest follow once it has returned.

That was built, and four probes in the live instance killed it.

1. **`Pick Rest` hanging off the first call's output: correct ordering, silently wrong data.** The rest lane started 16 ms after the first call ended, exactly as intended. But n8n carries an item's ancestry in `pairedItem`, and a lane fed from a node that emitted one item collapses every later item's ancestry onto that one. `Assemble Drafts` does `$('Assess Grounding').item`, so with a 3-item batch items 2 and 3 both resolved **item 1's** facts — no error, no warning, just the wrong lead's therapeutic areas and trial in the wrong lead's email. `Apply Claim Check`'s `$('Approval Gate').item` and `Assemble Follow-Up`'s `$('Build Follow-Up').item` have the same shape. This is the Workflow 5 view bug's family — a silent full-scale wrong result in the one place that is supposed to be careful.
2. **The lineage-preserving variant** — tag every item in one Code node, split with an IF (so both lanes keep their ancestry), and order the lanes with a `chooseBranch` Merge that waits for the first call — **resolved every item correctly** (tags a/b/c/d to items 1/2/3/4) and kept the ordering (gap 54 ms). It then **stopped the workflow dead on a one-lead batch**: the IF's false branch produces no items, so the Merge's second input is never satisfied, so nothing downstream runs at all. No draft written, no error, the lead silently left at `contact_found` after a paid call. The measured history says **a one-lead batch is the commonest size**.
3. `alwaysOutputData` on the IF does not rescue that: still dead at the first call.
4. The distinction that explains both: **a Merge input is satisfied when its upstream node RAN, even producing zero items, and unsatisfied when that node never ran.** An append-mode Merge whose empty side came from a Code node returning `[]` emits fine; the same Merge whose empty side is an IF branch with no items does not.

**So caching ships without the split**, one HTTP node per call site, and the reads come from the next run inside the 5-minute window rather than from within the batch. Measured, that is most of the benefit: Section 4's warm run read on every call. **What would make the split safe** is removing the dependency it breaks — have `code_assemble.js` and `code_approval_apply.js` resolve their upstream item **by `lead_id`** out of `$('<node>').all()` instead of by `pairedItem`, which is explicit, testable, and equivalent whenever the pairing is intact. That is a change to the two most safety-critical Code nodes in the project and wants its own mutation tests and a dry run, so it is an open item (Section 13), not a thing to slip in beside a cost optimisation.

### Workflow 5 — Exceptions Queue (HUMAN) — was the Review Queue
**Changed 2026-10-03 (migration `014`): the review queue is now an exceptions queue.** An email draft — first touch or follow-up — no longer waits for a human by default. The workflow that wrote it approves it (`approved_by = 'auto'`) when, and only when, all of these hold; anything else is written `pending` with the reason in `hold_reason`, and *that* is the queue:

| Rule | Held as |
|---|---|
| `settings.auto_approve_email` is on (on by default; off, nothing auto-approves and no claim check is paid for) | `auto-approve-off` |
| it is an email — **a LinkedIn draft never auto-approves** (Section 6) | `linkedin` |
| it is not a low-context note, nor a `no-send-clock` note | `low-context` / `no-send-clock` |
| its lead's country has a Send business-hours clock (Section 12) — held at once, never repaired: no rewrite can give a country a clock, and Send would refuse the email anyway | `no-send-clock: <country> has no business-hours clock, so this email can never be sent (Section 12)` |
| zero rule tags: nothing after `+` in `variant` (every Workflow 4 / skill v3 rule tag, `unconfirmed-claim` included) | `rule-tags: ...` |

(BEN-SEE)`, `claim-check-incomplete: ...`, `claim-check-failed: ...`; after repairs, every attempt's reasons: `first draft: … \| after repair 1: … \| after repair 2: …` |

**How it is built.** Two Code nodes, `n8n/drafting/code_approval.js` (Approval Gate) and `code_approval_apply.js` (Apply Claim Check), sit between Assemble and Write in Workflow 4 and in Follow-Ups, embedded verbatim in both, so a first touch and a follow-up are judged by the same functions. The clock list is the one constant substituted into that file at build time, from Section 12's own table, by whichever generator embeds it — so Drafting and Follow-Ups cannot end up judging one draft against two different lists, and neither can disagree with Send. The deterministic rules run first, so a draft they hold costs no API call. The checker gets exactly what the drafter had — the lead's fact sheet, including the ClinicalTrials.gov trial, which is looked up per run and stored nowhere, so this could not be a separate after-the-fact workflow — and, for a follow-up, the enrichment record plus the first email as context (the record holds no trial: a follow-up that states something about the trial is held, but one that only mentions it while referring back to the first email is judged a reference — measured 2026-10-03, draft 107 named "the INM004 trial" that way and passed). **The model judges statements; code decides.** Its schema has no overall verdict: it returns every statement sentence by sentence with a kind (claim / prospect / none), the claim code or record fact it compared it with, and a verdict, and Apply Claim Check approves only if every claim is `supported` by a code that really is a confirmed line, every prospect fact is `supported`, and the quoted sentences account for the whole email — a sentence it skipped is one nobody judged. A failed call (HTTP error, refusal, cut-off, wrong schema) holds the draft; there is no fallback model. The system prompt's example of a widening is deliberately *not* draft 99's sentence, which is the held-out case the dry run proves the check catches. Migration `014`'s trigger re-checks every deterministic rule on the table and turns a bad auto-approval into a hold, so a bug in the workflows can make them approve less, never more (Section 8).

**The repair loop — added 2026-10-03; the gate and the checker are exactly as strict as before.** When the claim check holds an email (first touch or follow-up) because it found statements that say more than their source — `widened` or `unsupported` claims, `unsupported` or `joined` prospect facts — the draft is not held yet. Apply Claim Check sends the drafting model (Section 3's model and parameters, never a cheaper one) the email, the confirmed lines, the prospect record and **each flagged sentence with the checker's exact reason**, and asks for a rewrite of those sentences only, in the approved claim's own words, adding nothing. Its answer is a list of `{original, replacement}`; `code_approval_repair.js` applies it **by code**, only to sentences the checker flagged and only inside the fields the email's text came from, so a repair cannot change anything else (a rewrite of an unflagged sentence is ignored). The repaired composition then runs through a second copy of the workflow's own Assemble node — every rule again, the same code — then the Approval Gate (rules 1–4) and the claim check, unchanged. **At most 2 repairs.** A pass at any attempt approves it (`approved_by = 'auto'`). A hold the composer cannot fix — a failed call, quotes that do not cover the email, a "supported" claim citing no confirmed line — is not repaired. **"Held" now means:** for a claim-check failure, still failing after the repairs (or a repair that failed or changed nothing); for rules 1–4 (the flag, LinkedIn, low-context, tags, unconfirmed codes), held at once, no repair — a rewrite that breaks one of them is held by the gate copy too. Every attempt is recorded: `hold_reason` lists each attempt's reasons, labelled (`first draft: … | after repair 1: … | after repair 2: …`), and `drafts.claim_check.attempts` keeps each attempt's verdicts, the rewrites that produced it, and the cost of its check and its repair, with the composing cost alongside — so a draft's cost includes its repairs. Follow-up #1 is now also told to use its added line almost word for word (skill §8, Workflow 6), the sentence every earlier hold came from.

**Send is unchanged** (the ceiling, business hours and every guard): an auto-approved email is an approved email, and goes out in its recipient's business hours like any other.

**What the human does now.** The NocoDB grid on `drafts` is still the interface and Approve · Edit · Reject still apply, with **rejection still requiring a reason** (bad fit / bad draft / already contacted / wrong contact — the learning loop's training data). What needs a person is every `pending` draft: each LinkedIn DM (always — Section 6), and every email the checks held — after its repairs, for a claim-check failure — with `hold_reason` saying why, attempt by attempt. A human approval is recorded `approved_by = 'human'`, and the hold reason is kept, so a held draft a person approves anyway is the evidence for tuning the checks. To stop an auto-approved email before it goes, reject it; editing its text makes the approval the human's. **The Daily Digest** (Workflow 6) reaches the operator once a day, from 08:00 PKT — before India, the earliest recipient, opens — listing every draft auto-approved since the last digest, every email sent and who approved it, and every pending draft with its reason. **The most serious bug found in this project, do not repeat it.** A Postgres view has no primary key and cannot be given one (error 42809). Without a PK, NocoDB cannot scope a write to one row — a single approve click on one draft went out as an unqualified `UPDATE review_queue SET status='approved'`, and an INSTEAD OF trigger applied it to every row in the view. It then returned an unrelated error, making the mass-approval look like a failed no-op. **This is the dangerous shape: silent full mutation plus a misleading failure signal**, in a workflow whose entire purpose is a human gate before sending. Fix: the view is read-only, so any write attempt fails loud and immediate (error 55000) instead of silently succeeding somewhere. NocoDB writes directly to `drafts` (which has a real PK), with approve/edit/reject validation enforced on `drafts` itself so it holds for every writer, not just NocoDB's UI. Any future change to this view's schema must re-verify this — confirm a real write behaves correctly against live data, never assume a clean join means a clean write path.

### Workflow 6 — Send & Track
**Send trigger:** Cron, business hours only, randomised intervals.
**Guard:** query today's send count; abort if at the warm-up ceiling. Ceiling is enforced in the workflow, not by discipline.
**Send:** SMTP node → mailbox. Log to `outreach_log`.
**Reply detection:** IMAP trigger polls the same mailbox. Any reply → kill follow-up sequence, set `status='replied'`.

**No HubSpot account exists yet — deferred, not dropped.** Original spec created a HubSpot deal on reply; skipped for now rather than routing into the wrong account (this pipeline's sender is Abdullah/Amitrix Labs, not the Fatima/NoblePath HubSpot the doc originally assumed). Re-adding a real CRM later is a small addition on top of this, not a rebuild.
**Opt-out detection:** reply matching no/unsubscribe/remove/stop → add domain to `blocklist`, permanent.

Section 13 carried "the reply assistant is half-built" as an open item since 2026-10-08; this closes it.

**`reply0001` (`n8n/workflows/reply-assistant.json`) — the draft and the code.** Every 30 minutes (a minutes interval, never an hours one — the Follow-Ups lesson, Section 9 above): `Find Replies To Answer` reads every `inbound_messages` row classified `reply`, matched to a lead, with no `reply_approvals` row against its Message-ID yet — one drafted reply per prospect **message**, for ever, so a rejected reply is never silently redrafted (delete its `reply_approvals` row to ask for another) and a prospect who writes again gets a fresh answer because that is a new Message-ID. The blocklist is checked here too, so a prospect who replied and then opted out costs no model call. `claude-sonnet-5-5` at effort `high` (Section 3) drafts the answer from their message, the thread as sent, the enrichment record's boundary facts and the confirmed claims — the **only** model call in the reply path, because the operator reads every one, so no claim check runs on it. Five topics nothing confirmed can settle (pricing, integrations, languages, security, timelines) are detected in **their** text and the model is told to defer them, rather than tagged afterwards for having guessed. `Assemble Reply` enforces the reply's own rules on top of Workflow 4's claim rules (embedded verbatim, same as Follow-Ups): 40–120 words, one next step, the Section 5 one-URL cap, and — Section 8's terminology decision, extended here on 2026-10-09 — **a reply never reuses the "two CROs" proof line and never calls Vertex Clinical Research a CRO**, because it is a clinical research centre, not a contract research organisation; both are refused on text alone (`proof-refused`), checked against every active claims-library line, not only the two that currently mention Vertex. `Write Reply Draft & Issue Code` writes the draft `pending` — **a reply is never auto-approved; migration `018` refuses one on the table as well as in the workflow** — and mints its one-time code through `reply_approval_issue()` (migration `018`, below), the function that knows to reuse an already-open code and reap a dead one rather than mint a second. `Build Review Email` sends the operator (their own inbox, never the outreach mailbox, so it uses no warm-up slot) what the prospect wrote, the exact bytes that would be sent, what the reply does **not** answer and why, the rule tags, and the three commands — `APPROVE <code>`, `REJECT <code>`, `EDIT <code> <replacement>`. A separate lane finds every open code the operator has not been told about in 4 hours (or at all — the self-heal for a review email or a digest send that failed) and reminds them with the same three commands; both lanes stamp the same "the operator has been told" statement, so that can only mean one thing.

**The operator fork in Mailbox Watch — the hazard this whole workflow exists to remove.** The operator answers the review email, and that answer is a reply **inside the prospect's own thread**: the review email quotes it, so References carries our Message-ID and `Record Inbound`'s strongest matcher (`thread`) would tie the operator's "no" to the prospect's lead and blocklist a real prospect permanently, with no error anywhere. So `Classify Inbound` parses the operator-command shape **first**, from the same text the reply classifier reads, before any reply classification is acted on, and `Command Shaped? → Apply Operator Command → Operator Mail?` all run **before** `Record Inbound` ever sees a command-shaped message — a plain "no" from the operator is not command-shaped at all and goes straight to `Record Inbound`, which independently refuses to match the operator's own address to any lead (migration-008's `settings.operator_email`, re-read there, never baked in). Three separate questions, deliberately not conflated (`code_operator_command.js`): **record** (is this command-shaped at all — every one gets an `operator_commands` row, accepted or refused, keyed on Message-ID so a re-delivery acts once), **handled** (is it really authenticated — SPF, DKIM and the sender all equal `settings.operator_email` — then it is operator mail and is never a prospect reply, whatever its code says), **accepted** (handled, and nothing else refused it — only then does a draft move). `Apply Operator Command` re-derives all three from the database at write time rather than trusting the read `Load Command Context` took moments before — the same direction of safety as `Decide Send`/`Claim Send`: a bug here can refuse a real approval, it cannot accept a forged one.

**`sendreply0001` (`n8n/workflows/send-reply.json`) — a separate lane, by design, from the cold `send0001`.** An answer to a message a prospect sent **us** is not cold outreach: Section 9, Workflow 7 skips the warm-up ceiling, the recipient's business hours and the pacing floor — `Load Reply Send State`'s query carries no clock table and no warm-up count to even consult, structurally, not merely by omission in the decision code. **What it never skips:** the blocklist, on both the lead's domain and the address actually being answered (an opt-out is still instant and permanent); the one-time code, re-checked at claim time with outcome `approved` or `edited` and belonging to *this* draft; the Section 5 signature and one-URL cap; and at-most-once (the draft flips to `sent` and an `outreach_log` claim is written before the SMTP call, exactly as the cold path). `d.variant LIKE 'reply/%'` is the entire boundary between the two lanes' queries, so no draft is ever visible to both and neither can disagree about which rules apply to it. It threads through the `smtp-send` sidecar rather than the installed Send Email node, below.

**Why a sidecar, not the installed Send Email node.** Read on 2026-10-09: n8n's Send Email node builds nodemailer's `mailOptions` from a fixed field set with no `headers` option, so it cannot set `In-Reply-To` or `References` — and a reply with neither is not a reply in anyone's mail client. `smtp_send_server.py` is a small HTTP service (`POST /send`) that builds the message with both headers from what the database really holds (falling back to the two Message-IDs it has rather than inventing a chain for a longer thread) and answers in nodemailer's own shape — `{accepted, rejected, messageId, response, error}` — so `code_check_smtp.js`, shared verbatim with the cold path, classifies a failure identically on both lanes. It refuses to send as any From but the configured mailbox. **Containment, in `docker-compose.yml` (`smtp-send` service), and asserted at build time, not only written in a comment:** it holds only `NOVASCOUT_MAILBOX_ADDRESS`, `NOVASCOUT_MAILBOX_PASSWORD`, `NOVASCOUT_SMTP_HOST`, `NOVASCOUT_SMTP_PORT` and `NOVASCOUT_SENDER_NAME` — no IMAP settings, no Anthropic key, nothing beyond what sending as this one mailbox requires — code mounted read-only, a read-only filesystem, no root (`user: "65534:65534"`), and **no published port**: it has no authentication of its own, so it stays reachable only on the compose network, and `build_workflow.py` refuses a `ports:` entry on it the same way it already refused one on `imap-health`.

**Migration `018` — the rules the workflow above needs, on the table, for migration `014`'s reason: a rule there holds for every writer, not only for the workflow that was careful.** (1) `reply_approval_new_code()` / `reply_approval_issue()`: the one definition of how a code is minted, reused (an already-open code for that draft, never a second one — `reply_approvals_one_open_per_draft`) and reaped (an expired, never-used code is deleted first, so it cannot block its own replacement forever). Both callers that need a code — this workflow for a drafted reply, the Daily Digest for a held email (`kind='email-hold'`) — use this function; neither mints its own row. (2) `drafts_approval_rules()` gains the reply branch: a `reply/` draft may only become `approved` while a one-time code for it is open or was already used to approve/edit it — **this is Workflow 7's entire security model expressed where it cannot be bypassed**, including by the NocoDB grid, a direct `UPDATE` in psql, or the workflow that wrote it — and `approved_by = 'auto'` on a reply is refused by name, because no claim check ever runs on one. (3) A replied lead's pending or approved LinkedIn DM is retired automatically (`retire_linkedin_on_reply()`, a trigger on `inbound_messages`): Section 13 carried this as an open decision since 2026-10-07 (lead 26's DM 111 sitting `pending` after the lead replied by email), and it is decided here as the first of the two options that row offered, plus the one-off backfill for lead 26 and anyone else already in that state.

**Proven by `n8n/sendtrack/dryrun/reply_dryrun.py`, 27/27 checks, 2026-10-09 — the real `mailwatch-test.json` and `sendreply-dryrun.json` variants (the same node lists that ship; `build_workflow.py`'s own assertion is that credentials, Config and the sink URL are the only differences) through n8n, against a scratch Postgres with migration `018` applied to the scratch copy only (the live database did not have it yet — see §13), an HTTP sink standing in for `smtp-send`, and the existing SMTP sink for every operator notification. The live database's fingerprint was unchanged before and after.** Proven there, by the actual database state after each run, not by the model's own proposed verdict: a **spoofed sender** (real SPF+DKIM for its own domain, wrong From) is refused `not sent from the operator address`, its code left open and its draft left pending; a **wrong, shape-valid but nonexistent code** is refused `no such one-time code`; an **expired, never-used code** is refused with the moment it expired; a **reused code** — the same code quoted a second time, both messages authenticated and processed in the same run — is refused at write time even though n8n evaluates one node across every item before the next node starts on any of them, so the stale per-item proposal for the second message said `accepted`; `Apply Operator Command`'s own re-derivation, inside its own transaction, is what actually catches it, and `reply_approvals.used_by_message_id` names the first message, never the second; a **plain "no" from the authenticated operator** is never recorded as a command and is recorded by `Record Inbound` matched to no lead at all, so it blocklists nothing; a **real prospect's plain "no"**, in the very same run, still matches their lead by `contact-email` and blocklists their domain, permanently, by the same statement that classified it; and an **approved reply** sends despite a clock set to 02:00 UTC and 20 cold sends already logged that sender-day (a maxed week-4 ceiling) — and is refused once its recipient's domain is blocklisted, with no HTTP call made and the draft left exactly `approved`, not `sent`.

**A real bug the dry run found before anything touched a live system, not after.** `with_iso()`, the build-time macro that turns `ISO(x)` into the `to_char(...)` expression every clock value is sent across as, carried a literal backspace byte inside its own regex (between `r"` and `ISO`) — invisible in an editor, so it matched nothing at all, and **every `ISO(...)` call in every generated statement had been shipping as the literal, uppercase, unsubstituted text**, which Postgres has no function for. `Load Command Context` runs on **every** INBOX message, not only command-shaped ones (`Classify Inbound`'s edge to it is unconditional) — so this would have broken Mailbox Watch for all inbound mail, not only operator commands, the moment today's build was imported and a real message arrived. No earlier guard could have caught it: `build_workflow.py`'s own assertions check the generated JSON's shape and text, never execute the SQL, and this path had never been run against a real Postgres before `reply_dryrun.py`'s first execution. Fixed in the same function, two changes: the stray byte removed, and the regex widened (`(?:\(\))?`) to also match `ISO(now())` — the one call site whose argument is a function call rather than a dotted column reference, which the original `[\w.]+` class could never have matched even without the corruption.

**Offsets are standard time, with no DST — the 2026-09-14 operator decision, unchanged, now with wider consequences.** A country that observes summer time runs an hour later than this table for part of the year, so its send window reads 09:00–17:00 when the local clock says 10:00–18:00: the last hour of the window can land just after close. That affects Europe, North America, **Egypt** (which brought summer time back in 2023, so a core country is on the list), Israel, Lebanon, and the southern-hemisphere countries in their own summer — Chile, New Zealand and Australia's south-east. **Morocco is the one that drifts the other way:** it sits permanently on UTC+1 and steps back to UTC+0 for Ramadan, so during that month the table reads an hour *late* and the window lands at 08:00–16:00 local, which is harmless. **Paraguay, Jordan, Turkey, Mexico and Brazil are not on the list at all:** each abolished summer time and sits permanently on one offset (Paraguay UTC-3 since October 2024, Jordan UTC+3 since 2022, Mexico since 2022, Brazil since 2019, Turkey since 2016), which is what the table carries — the mistake to avoid there is writing the old *standard* offset and leaving the table an hour out all year instead of half of it. It never sends *before* 09:00 local, and never on a weekend. Fixing it properly means a real tz database in a Code node, which n8n's sandbox has no module for — revisit only if a reply says the timing was wrong.

**The weekend column is each country's statutory weekend**, not an assumption: Friday–Saturday across the Gulf and most of the Arab world plus Israel, Bangladesh, Algeria, Djibouti and Mauritania; Saturday alone in Nepal; Saturday–Sunday everywhere else, UAE included (it moved in 2022), and in Lebanon, Morocco and Tunisia.

**A lead whose country has no clock is stopped before any money is spent (2026-10-07).** Three places, in this order: Assess Grounding (`n8n/drafting/code_assess.js`) takes it down the no-API branch and writes a `no-send-clock` note instead of calling the drafting model; the Approval Gate (`code_approval.js`, embedded verbatim in Drafting and in Follow-Ups) holds any email draft whose lead has no clock, with no claim check paid for; and Send refuses it as before. The note advances the lead to `drafted` for the same reason a low-context note does — a lead that produces no row is re-picked by every tick and starves the batch behind it. To rescue one: add its clock here and to `code_decide.js`, rebuild, re-import, and set the lead back to `contact_found`. **Proven by unit tests and mutations, not by a live execution** — with the table covering every included country there is no lead left to fire it on, which is the point: `test_grounding.js` has 11 cases on the branch and the note it writes, `test_approval.js` 6 on the gate's rule, and `test_approval_mutations.py` breaks that rule five ways and proves the suite fails each time. ## 14. Related: Nova Chatbot Model Migration (separate project)

Not part of Nova Scout, tracked here to keep the decision record in one place.

**Proposal:** migrate Nova Agent Kit from Haiku 4.5 to Sonnet 5.

**Cost reality:** Sonnet 5 is $2/$10 vs Haiku 4.5 at $1/$5 — double, not cheaper. At Nova's volume with a ~17K-token context-stuffed system prompt on every turn, this is a real increase, not noise. Still comfortably absorbed by the $300/month per-tenant fee.

**Do this first, regardless of model choice:** enable prompt caching on the static system prompt. Cache hits bill at 10% of base input. On a 17K-token system prompt sent every turn, this cuts the input bill by roughly 90% — a far larger lever than model selection, and it makes the Sonnet upgrade close to cost-neutral.

**Migration risks — test before deploying:**
- The reliability scaffolding (forced `tool_choice`, keyword triggers, `request_missing_information` guard) was engineered against Haiku 4.5's specific failure modes. Sonnet 5 fails differently. It may allow removing some scaffolding — verify, don't assume.
- Re-test the field-fabrication guard specifically. That bug drove real design decisions.
- Check whether extended thinking is on by default. Thinking tokens hurt time-to-first-token, and the widget UX depends on the response feeling instant.

**Rollout order:** Vertex staging tenant → all six flows end to end → NoblePath production. Never NoblePath first.
